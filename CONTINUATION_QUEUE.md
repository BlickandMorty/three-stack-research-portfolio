# Research Continuation Queue

Use one of the phrases below when you want to resume a line of work. This queue prevents a project from turning into “run more things until a number looks better.”

## Default rule

**Do not start a new synthetic experiment by default.** The current release already has its results, nulls, controls, and stopping rule. The normal next activity is study, explanation, portfolio work, or external review.

## `continue research — UAS external corpus`

**Question:** Does typed record identity help on records that were not authored by the same person who built the retrieval system?

**Start only when all are ready:**

1. permitted public or independently authored source records;
2. a frozen retrieval hash and answer key before outputs are viewed;
3. a matched flat baseline that retains the same necessary information;
4. a separate case author and blind grader, or a documented equivalent;
5. at least one independent model or grader;
6. a planned place to publish a negative result.

**Do not do:** reuse the old synthetic cases, remove information from the flat baseline, or tune retrieval after seeing the scored cases.

## `continue research — compression behavioral preregistration`

**Question:** Can a fixed control help with answerable compressed cases without increasing fabricated answers or harming clean cases?

**Start only when:** a new task family has a pre-intervention baseline test showing real answerable-case competence. The previous behavioral task had universal abstention, so it could not measure improvement or damage.

**Must include:** frozen cases, fixed control choice, same-norm random control, clean-context condition, abstention/fabrication metrics, and a negative-result plan.

## `continue research — science provenance`

**Question:** Can a small public science-source workflow preserve evidence and expose uncertainty without pretending to make a scientific discovery?

**Start only when:** the exact public sources, permission/terms, outcome measure, and failure condition are written down first.

**Good scope:** one narrow, public dataset or set of published tables; citation/address validation; uncertainty or missing-data audit.

**Not the scope:** medical advice, clinical prediction, or an unreviewed claim about biological truth.

## `continue research — security evidence lab`

**Question:** Can a safe, authorized lab produce a clear observation and report without overclaiming what a scan or capture means?

**Start only when:** the target is self-owned or explicitly authorized and the reporting question is stated first.

**Good scope:** localhost/service inventory, packet-capture interpretation, Windows event review, defensive configuration comparison, or a synthetic policy evaluation.

**Not the scope:** probing systems you do not own, bypassing protections, or treating a lab observation as an incident finding.

## `continue research — Epistemos layer audit`

**Question:** What does the current repository actually show about one subsystem?

**Method:** choose exactly one subsystem—editor, search, graph, vault context/provenance, sync, or Windows scaffold—then inspect the current tree, relevant historical commits, tests/CI, and known gaps. Update the layer map only with evidence.

**Good outcome:** a clearer explanation, a documented bug/recovery boundary, or a fresh test result. This does not require inventing a new feature.

## `continue research — study one project`

Use this when the goal is learning rather than producing another result. Pick one project from [PROJECT_LAYERS.md](PROJECT_LAYERS.md), then answer four questions in your own words:

1. What question did it ask?
2. What went in, and what changed?
3. What result happened?
4. What does that result still not prove?

The best starting order is: Epistemos + Instant Recall, UAS, Dose-Response, State Transport, then the advanced math/formal projects.

## `continue research — public explanation`

Turn one already-verified project into a post, result figure, README improvement, or portfolio section. Start with the simplest claim and keep the controls/failure visible. The first recommended pairing remains:

```text
Epistemos workspace development surface
  +
Instant Recall GitHub card
```

Do not publish a LinkedIn post or send messages without confirming immediately before that external action.

## Parked ideas: do not describe them as results

- functional valence or emotion-like control;
- Eidos evidence admission;
- SCOPE-Rex routing;
- broader canon claims;
- a general UAS architecture claim;
- an Epistemos Windows product claim while native-host CI is failing.

Each can become a future research direction only after it has a small falsifier, frozen protocol, saved artifact, and stated boundary.
